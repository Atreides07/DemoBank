# Методика проверки производительности

Цели PERF-01…PERF-09 зафиксированы в [требованиях](requirements.md). Для переходов внутри приложения целевой p95 составляет не более 100 мс. При частоте экрана 60 Гц бюджет стадий UI и raster — примерно 16,7 мс каждой, а доля кадров сверх бюджета в контрольной прокрутке длительностью не менее 60 секунд должна быть меньше 1%. История проверяется на наборе не менее 10 000 операций с ограниченным числом загруженных страниц. Успешная сборка и средний FPS не заменяют эти измерения.

## Условия прогона

Физическое USB-устройство — **realme RMX3760**, Android 15, платформа `ums9230`, экран 720 × 1600, плотность 2,0, частота 60 Гц. Значение `MemTotal` — 5 905 892 КиБ, то есть около 6 ГБ. Объём памяти выше целевых 3–4 ГБ, поэтому результат относится к этому устройству и не подтверждает скорость или расход памяти на телефоне с 3 ГБ.

Контрольный набор содержит 12 000 операций; демонстрационная дата — 16.10.2026, seed — 42. Первая страница содержит 30 операций. Применённая версия истории удерживает не более пяти полных страниц, то есть 150 моделей. Во время обновления старая версия остаётся доступной для чтения, а новое окно подготавливается отдельно: первая страница, страница опоры и максимум два её соседа. Поэтому дополнительно допускается до четырёх страниц / 120 моделей новой версии. Общий постоянный буфер двух версий ограничен девятью страницами / 270 моделями; после применения ссылка на ожидающее окно освобождается. Счётчик `state.pages` измеряет только применённую версию; обе версии и временные сетевые буферы входят в RSS. Это различие фиксируется до отдельного прогона обновлений.

Кеш ответов ограничен 120 записями и 1 МиБ на запись. На нативных платформах операции SQLite выполняются в изоляте Drift. Синтетические данные создаются порциями с передачей управления, чтобы генерация набора не блокировала интерфейс.

Профиль `slow` задаёт начальную задержку 1100 ± 300 мс, скорость 18 000 Б/с, размер порции 1024 Б и дополнительную задержку следующей страницы 800 мс. Эти условия фиксируются до измерений. Для данного профиля приняты цели: серверная обработка и сериализация JSON — p95 не более 16 мс; получение первой страницы — не более 3,5 с от отправки запроса; кадр с готовыми данными — не позднее 100 мс после завершения запроса. Последний интервал требует сопоставления сетевых событий с кадрами: полное время до готовности данных само по себе его не доказывает. Для HTTP отдельно фиксируются сервер, транспорт и сетевые задержки.

## Запуск на устройстве

Из каталога `apps/bank_app`, с подключённым физическим устройством:

```sh
flutter drive --profile --no-dds --endless-trace-buffer \
  --driver=test_driver/performance_driver.dart \
  --target=integration_test/performance_test.dart \
  --dart-define=PERF_PROBE=true \
  --dart-define=DATA_SOURCE=simulation \
  --dart-define=NETWORK_PROFILE=slow \
  -d DEVICE_ID
```

Параметр `--no-dds` обязателен для используемого сбора `traceAction`: наблюдавшийся запуск без него завершился до получения измерений. Такой сбой не является результатом проверки скорости.

Команды Flutter для одного приложения выполняются последовательно. Даже `drive --use-application-binary` обновляет зависимости и регистрацию плагинов: параллельная release-сборка того же приложения может получить регистрацию тестового плагина и завершиться ошибкой Java. Перед следующим запуском проверяется код завершения сборки, а APK копируется в отдельный файл. Обычная сборка после интеграционных проверок выполняется с обновлением зависимостей, без `--no-pub`.

Для отдельного прогона через настоящий HTTPS используются `DATA_SOURCE=http` и `API_BASE_URL`, как описано в [README](../README.md). На сервере также должен быть выбран профиль `slow`. Результаты двух источников сохраняются отдельно; успешная симуляция не подтверждает работу реального транспорта на Android.

Политика соединений — дополнительное условие HTTPS-прогона. По умолчанию `HTTP_KEEP_ALIVE=true`. Для проверенного проблемного временного туннеля используется явный `--dart-define=HTTP_KEEP_ALIVE=false`, согласно [ADR 0006](adr/0006-http-connection-policy.md). `device_profile`, `interaction_profile` и release-отчёты сохраняют `httpKeepAlive` из созданного API-клиента. Успех этого режима не приписывается исходным попыткам с пулом. Тайм-ауты, сценарии и численные пороги одинаковы; в приложении сохраняется обычная параллельная загрузка.

## Что собирает тест

Тест использует `LiveTestWidgetsFlutterBindingFramePolicy.benchmarkLive`. Он прокручивает рабочую историю со сворачиваемой панелью не менее 60 секунд, собирает `FrameTiming` стадий UI и raster и сохраняет сырые события через `binding.traceAction` с потоками `Dart`, `Embedder` и `GC`. После прокрутки выполняются шесть циклов по четырём основным вкладкам — **24 перехода**.

Границы прокрутки фиксируются номерами кадров движка. Дополнительные две секунды нужны только для получения отложенных пакетов `FrameTiming`: кадры этого ожидания исключаются из распределений и знаменателя процента. Такой же принцип используется в отдельных interaction-стадиях. В baseline, снятом до этой правки harness, idle drain ещё входил в счётчик; окончательные отчёты содержат `frameIdStartExclusive` и `frameIdEndInclusive` для проверки точного диапазона.

Результат драйвера записывается в `.artifacts/performance/android-profile.json`. Раздел `device_profile` содержит условия, распределения времени кадров, сетевые события, счётчики страниц и образцы RSS. Раздел `scroll_timeline.traceEvents` содержит события для импорта и исследования трассы. Сводные процентили `FrameTiming` не заменяют эту трассу. До следующего прогона отчёт копируется под отдельным именем, например `android-profile-simulation.json`; вместе с ним сохраняются сведения об устройстве и версии сборки.

Кадр считается вышедшим за бюджет, если `buildDuration` **или** `rasterDuration` превышает 16 667 мкс. Это проверка длительности стадий Flutter. Она не равна прямому подсчёту пропущенных обновлений физического экрана и не включает всю цепочку от системного ввода до появления пикселей.

## Границы метрик

| Метрика | Что измеряется | Ограничение |
|---|---|---|
| `firstWidgetFrameMs` | Построение оболочки с `DsHomeHeader` после `pumpWidget` | Не включает запуск процесса и предварительную очистку кеша |
| `coldFirstPageFrameworkFrameMs` | Кадр после готовности первой страницы при пустом кеше ответов | Хранилище уже открыто очисткой; это не холодный запуск SQLite. Строки могут находиться ниже видимой области |
| `firstPageRequestMs` | Реальная длительность первого успешного запроса истории в ApiClient | Включает получение и разбор ответа; не является временем одного серверного вычисления |
| `firstPageNetworkCompleteToFrameworkFrameMs` | Время от события завершения ApiClient до кадра с готовыми данными | Обе отметки снимаются одним Stopwatch через необязательный наблюдатель DI; включены запись кеша, доставка состояния и следующий framework frame. Системный показ пикселей отдельно не измеряется |
| `cachedFirstPageFrameworkFrameMs` | Готовность первой страницы после повторного подключения приложения к тому же окружению | Это показ кешированных данных, а не повторный запуск процесса |
| `navigationHandlerToFirstFrameMs` | Время от обработчика навигации внутри приложения до следующего кадра framework | Не включает доставку системного ввода и завершение raster/presentation |
| `navigationDriverTapToPumpMs` | Время от вызова нажатия тестовым драйвером до следующего `pump` | Включает работу драйвера; учитывается отдельно от внутренней реакции приложения |
| `ProcessInfo.currentRss` | Резидентная память процесса в контрольных точках | Не является Android PSS; в симуляции включает данные локального источника |

Холодный запуск Android измеряется отдельно:

```sh
adb shell am start -W -S -n dev.demobank.bank_app/.MainActivity
```

`LaunchState` и `TotalTime` описывают запуск Activity. Они не показывают время получения первого сетевого содержимого. Повторный запуск и возврат в приложение также фиксируются отдельно. Внутренний обработчик навигации не покрывает системную доставку ввода и показ кадра; отдельный сборщик ниже измеряет первый ответ поверхности через present fence.

Системный FrameTimeline не подменяет эту границу автоматически: [документация Perfetto](https://perfetto.dev/docs/data-sources/frametimeline) указывает ограничение для SurfaceView, который использует текущий Flutter Android renderer. Поэтому чужие HWUI/Activity кадры нельзя выдавать за показ Flutter-поверхности. Отчёт сохраняет эту границу вместо недоказанного системного процента.

## Контрольные сценарии

1. **Пустой кеш.** Сопоставить готовность оболочки, события запроса (`start`, `headers`, `chunks`, `completed`) и кадр с готовой первой страницей. Проверить запрос 30 операций вместо загрузки всей истории.
2. **Свежий и устаревший кеш.** Показать пригодные данные до ответа сети. Ошибка обновления не должна удалять уже доступное содержимое.
3. **Прокрутка не менее 60 секунд.** Проверить сворачивание и раскрытие панели, загрузку страниц и обратное чтение после вытеснения из памяти. Сохранить UI/raster p50, p95, p99, максимум и долю кадров сверх бюджета.
4. **Повторные маршруты и память.** Выполнить шесть циклов по вкладкам и проверить детализацию. Сопоставить RSS, Android PSS из `dumpsys meminfo`, число страниц, контроллеров и подписок. Оценивать стабилизировавшиеся значения; одна пара замеров не доказывает отсутствие утечки.
5. **Изменения истории.** Сменить фильтр, получить фоновые новые операции, удалить читаемую опору и прервать переход. Проверить сохранение контекста и бюджет кадров в полном и немедленном режимах обновления.
6. **Медленная, нестабильная и отключённая сеть.** Проверить навигацию, нажатия и прокрутку загруженных данных до завершения запроса. Повторить применимые сценарии с симулятором и настоящим HTTP-транспортом.
7. **Сценарии в release.** Отдельно выполнить `journey_test.dart` в `bank_app` и `fines_app` до результатов платежей и аналитики. Функциональная проверка release и измерения profile учитываются раздельно.

Численный отчёт проверяется командой из корня репозитория:

```sh
dart run tool/check_performance.dart .artifacts/performance/android-profile-simulation.json
```

Проверка отклоняет debug, короткий прогон, недостаточный набор данных, превышение лимита страниц и отсутствие сырых событий трассы. Её успешный результат подтверждает только проверяемые показатели данного отчёта. Идентичность устройства, состояние памяти, системные задержки и человеческая оценка требуют своих доказательств.

## Отдельный профиль изменений истории и аналитики

Из `apps/bank_app`:

```sh
flutter drive --profile --no-dds --keep-app-running \
  --endless-trace-buffer \
  --driver=test_driver/interaction_performance_driver.dart \
  --target=integration_test/interaction_performance_test.dart \
  --dart-define=PERF_PROBE=true \
  --dart-define=NETWORK_PROFILE=slow \
  -d DEVICE_ID
```

Драйвер сохраняет `.artifacts/performance/interaction-profile.json`. Для HTTPS добавляются те же `DATA_SOURCE=http` и `API_BASE_URL`; серверный профиль указывается через `HTTP_PROFILE_DESCRIPTION`. Поэтапно записываются полный и немедленный переход, повторная смена фильтра до ответа, фоновая операция со сменой статуса, применение нового окна с читаемой опорой и путь по категориям и временным точкам аналитики. Подготовка опоры выполняется настоящими жестами и запросами, вне измеряемых стадий.

Для окончательного прогона оба сценария можно выполнить одним запуском: target `integration_test/acceptance_performance_test.dart` и driver `test_driver/performance_driver.dart`. Этот entrypoint последовательно регистрирует исходные тесты, не сокращая их сценарии. В `.artifacts/performance/android-profile.json` сохраняются оба раздела и все трассы; каждому источнику назначается отдельная копия отчёта. Окружение каждого теста создаётся и освобождается отдельно.

`FrameTiming` относится к стадии по номеру кадра движка; задержка доставки пакета измерений не приписывается соседнему переходу. Отдельно сохраняются UI, raster, vsync overhead, total span, обработчик → framework frame, готовность данных, RSS и сырой `interaction_*` timeline. Прохождение сценарных assertions не означает автоматического прохождения численных бюджетов: они оцениваются по каждой стадии, с учётом числа образцов. Сравнение этих технических режимов не заменяет человеческую проверку пользы.

После закрытия измеренного окна probe сжимает завершённую JSON-трассу без потерь (gzip/base64), чтобы миллионы Map-узлов прошлых сценариев не вызывали дополнительные UI-сборки мусора в следующих стадиях. Host driver восстанавливает исходный JSON и сверяет число событий перед сохранением; unit-тест проверяет точные временные метки, аргументы и метаданные, raw-аудит — покрытие каждого кадра. Сжатие/восстановление выполняется вне измеренных окон. Полный исходный timeline при этом сохраняется в отчёте. Диагностические буферы и получение текущей трассы всё равно входят в RSS процесса. Рост RSS такого прогона нельзя целиком приписывать прикладному кешу или считать доказательством утечки. Для оценки стабилизации памяти отдельно снимается PSS обычной пользовательской сборки при повторении маршрута. У стандартного timeline ring buffer ранние события длинной стадии могут вытесняться: полные образцы `FrameTiming` сохраняются независимо, а причины задержки исследуются только в фактически сохранившемся временном окне трассы. Поэтому окончательные команды используют штатный Flutter `--endless-trace-buffer`; его дополнительная память относится к диагностике, а не к обычной сборке. Прямой `--dart-flags=--timeline-recorder=endless` отклоняется Flutter engine до старта VM и не используется. После записи проверяется покрытие временного диапазона кадров, а не только наличие событий.

## Release-сценарии на Android

В используемом Flutter 3.35.7 `flutter drive --release` не поддерживается. Для AOT-сценария собирается отдельный APK с интеграционной точкой входа и включённым протоколом отчёта. Например, из `apps/bank_app`:

```sh
flutter build apk --release --target=integration_test/journey_test.dart \
  --dart-define=INTEGRATION_TEST_SHOULD_REPORT_RESULTS_TO_NATIVE=false \
  --dart-define=JOURNEY_SCREENSHOTS=false \
  --dart-define=JOURNEY_RELEASE_LOG=true \
  --dart-define=NETWORK_PROFILE=slow
cd ../..
python3 tool/run_android_release_journey.py \
  --adb adb --device DEVICE_ID \
  --apk apps/bank_app/build/app/outputs/flutter-apk/app-release.apk \
  --package dev.demobank.bank_app \
  --output .artifacts/release-journey-bank --timeout 600
```

Для самостоятельных штрафов сборка выполняется из `apps/fines_app`; используются APK этой папки, package `dev.demobank.fines_app` и отдельная папка результата. Для настоящего HTTPS добавляются `DATA_SOURCE=http` и адрес API при сборке. Перед каждым полным платёжным маршрутом HTTPS-сервер запускается с чистыми синтетическими данными: уже оплаченное начисление не должно снова предлагаться к оплате.

Runner устанавливает и запускает только указанный пакет и читает только его PID и тег `flutter`. Результат принимается при совпадении целого AOT-отчёта и итогового вердикта Flutter. При ошибке или timeout останавливается только тестовое приложение. Тестовый IME передаёт текст настоящему клиенту EditableText в AOT и проверяет введённое значение; это не проверка системной клавиатуры Android. На realme наблюдалась штатная проверка нового APK, перекрывающая Activity: после её успешного завершения приложение возвращается на передний план, а сорванная попытка не считается измерением.

Тестовый APK отделён от пользовательской сборки. После проверок обычная сборка создаётся командой `flutter build apk --release --target=lib/main.dart` и устанавливается для просмотра. Фактические результаты и незакрытые этапы приведены в [отчёте о проверках](verification.md). Невыполненный бюджет остаётся открытым до исправления и повторного измерения.

## Системные измерения обычного release

`tool/measure_android_release.py` работает с уже установленным банковским APK из `lib/main.dart`, без тестовой точки входа и `PERF_PROBE`. Он проверяет совпадение SHA-256 установленного `base.apk` с переданным файлом и передний план приложения. Сам сборщик ничего не устанавливает и не меняет системные настройки.

Сначала установить обычный APK, открыть главную и дождаться загрузки. Координату нижней навигации взять из свежего скриншота устройства. В выполненном прогоне 720 × 1600 это `y = 1405`; переносить её на другой экран без проверки нельзя. Центры четырёх вкладок сборщик рассчитывает по фактической ширине дисплея.

Скомпилировать `tool/android_input_marker.c` Android NDK для ABI телефона. Например, для использованного arm64 и macOS:

```sh
mkdir -p .artifacts/os-probe
DEMO_NDK=/path/to/android-sdk/ndk/27.0.12077973
"$DEMO_NDK/toolchains/llvm/prebuilt/darwin-x86_64/bin/aarch64-linux-android24-clang" \
  -std=c11 -O2 -Wall -Wextra -Werror -pedantic \
  tool/android_input_marker.c -o .artifacts/os-probe/input_marker
python3 tool/measure_android_release.py --phase startup \
  --adb /path/to/adb --device DEVICE_ID \
  --apk .artifacts/builds/bank-release.apk \
  --output .artifacts/performance/os-release
python3 tool/measure_android_release.py --phase routes \
  --adb /path/to/adb --device DEVICE_ID \
  --apk .artifacts/builds/bank-release.apk \
  --output .artifacts/performance/os-release \
  --nav-y 1405 --helper .artifacts/os-probe/input_marker
```

Каталог результата должен быть новым: существующие отчёты не перезаписываются. `startup` сохраняет три запуска с остановкой процесса и три возврата через Home; значения COLD/HOT берутся из ActivityManager, а не назначаются заранее. `routes` выполняет шесть циклов по четырём вкладкам и семь scoped-замеров Android PSS.

Перед каждым нажатием сравниваются два снимка истории кадров неподвижной Flutter SurfaceView. Нативный helper ставит `CLOCK_MONOTONIC` непосредственно перед `exec input tap`. После ввода выбирается первый новый завершённый present fence; desired/ready/actual timestamps должны следовать за marker. Сохраняются оба исходных снимка, последующий снимок, выбранная тройка и все значения PSS. Имена Android `RequestedLayerState{…}` приводятся к имени слоя, которое принимает `SurfaceFlinger --latency`.

Разность marker → actual present — консервативная оценка автоматического ввода до первого ответного кадра поверхности, включающая запуск утилиты ввода. Это не измерение физического пальца, распознавание содержимого нового экрана или время завершения всей анимации. Семантический переход отдельно проверяется UI-маршрутом. Значение тройки соответствует [реализации FrameTracker в AOSP](https://android.googlesource.com/platform/frameworks/native/+/51de481/services/surfaceflinger/FrameTracker.cpp).

Неполная выборка, неверный APK, отсутствие завершённого fence или неподтверждённый idle дают ненулевой код завершения с сохранением частичных данных. Статус `complete` означает достоверность сбора, а численный бюджет оценивается отдельно. Helper удаляется только из собственного временного namespace. Стабилизация PSS на этом маршруте не доказывает отсутствие утечек при любой продолжительности работы.


## Расширение сценария после предоставления скриншотов

Новая 60-секундная прокрутка проходит длинную витрину с ленивыми изображениями и порционную историю. В interaction harness сохранены все 14 исходных стадий и добавлены `account_open`, `account_collapse_restore`, `account_back`: всего 17. Пороги не меняются. Прогон включает реальные fling на счёте, закреплённый возврат и восстановление главной. Новые доказательства и сборки привязываются к отдельному снимку `reference-design`; старые результаты относятся к прежней композиции.

## Переходы страницы счёта

Новый image-heavy экран отдельно измеряется стадиями `account_open`, `account_collapse_restore`, `account_back`. Общий переход перемещает сохранённую `RepaintBoundary` без полноэкранного alpha-смешивания, а смещение округляется до физических пикселей: это позволяет переиспользовать атлас глифов. Reduced motion сразу показывает итоговое состояние. Исходные не прошедшие бюджеты прогоны сохранены отдельно; результат оптимизации принимается только по повторному физическому замеру.

Если Android после переустановки удерживает устаревший ProcessRecord, допускается остановка только пакета DemoBank, проверка SHA уже установленного profile APK, запуск с обычными Flutter extras `enable-dart-profiling`, `start-paused`, `endless-trace-buffer` и `flutter drive --use-existing-app` к его VM Service. Это не меняет код сценария, source digest или пороги. Стратегия запуска записывается в run metadata; сорванные старты не считаются измерениями.

Панели витрины используют физическую тень `Material.elevation`, а не отдельный Gaussian `BoxShadow`: это сохраняет мягкое разделение белых карточек без большого размытого промежуточного изображения. Контрольные сравнения сохранены отдельно; выбранный renderer и условия повторного замера описаны в [ADR-0007](adr/0007-android-renderer.md). Визуальные тесты явно ждут ImageStream перед снимком, не утверждая серые незагруженные картинки.

Индикатор `DsStatus` имеет собственную границу перерисовки: вращение загрузки не должно заново рисовать статическую поверхность, текст и соседей. Регрессия считает реальные вызовы `CustomPainter` вокруг статуса: до исправления очередной тик давал лишний paint, после исправления счётчик не меняется. Это локальное доказательство изоляции отрисовки; численный эффект оценивается отдельно физическим SIM/HTTPS-прогоном.
