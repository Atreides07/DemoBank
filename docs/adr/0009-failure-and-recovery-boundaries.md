# ADR 0009: ошибки кеша и восстановление операций

Дата: 18 октября 2026 года. Статус: принято и реализовано в текущем рабочем дереве.

## Обоснование

Общая обработка ошибок скрывала серверный успех при сбое кеша, блокировала сеть повреждённым профилем и называла отказ справочника повреждением журнала. После изменения ввода UI мог сохранить старые начисления, а повтор фильтра — выполнить другой запрос.

## Решение

1. **Кеш необязателен.** DTO проверяются до кеширования. `CacheStore.writeResponse` диагностирует сбой записи, сохраняя серверный результат. Нечитаемая копия считается промахом; ошибка чтения не блокирует сеть.
2. **Журнал обязателен.** Резервация использует `write`, возвращающий ошибку. Пока запись не сохранена, отправка запрещена. Очистка response cache не очищает journal.
3. **Ответ сверяется до очистки.** Checkout проверяет соответствие pending-записи; операция со счётом — непустой ID результата, `requestId`, сумму и валюту. Несовпадение сохраняет неопределённый результат и прежний ключ.
4. **Восстановление не зависит от справочника.** Сохранённый перевод открывается без загрузки получателей. Для нового перевода отказ справочника имеет код `recipientsUnavailable` и повтор загрузки.
5. **Новый ввод сбрасывает выбор.** Изменение документа/лицевого счёта очищает начисления, выбор и меняет поколение запроса. Старый ответ игнорируется.
6. **Повтор сохраняет фильтр.** Старые данные остаются со своим фильтром; история и аналитика отдельно помнят неудавшийся. `retry` запрашивает его и блокирует параллельный повтор.

## Ограничения

После отказа записи кеш может остаться старым или отсутствовать; следующее чтение сверяется с сервером. Диагностика содержит тип ошибки без тела ответа.

Native-журнал сохраняется в SQLite. На web отказ localStorage может привести к успешной записи только в память сессии, без гарантии сохранности после закрытия браузера. Вместо недоступного имени получателя восстановленный перевод может показывать сохранённый идентификатор.

Неподтверждённый результат не удаляется ради нового платежа. Безопасность повторов зависит от журнала и серверной идемпотентности. Автоповторы POST не добавлены; сохранность HTTP DemoApi после перезапуска сервера не гарантируется.

## Альтернативы

- Любой сбой хранения считать отказом — исказит результат после серверного успеха; подавлять все ошибки — отменит обязательность журнала.
- Считать HTTP 200 успехом — не проверяет соответствие операции.
- Повторять отображаемый фильтр — после неудачной смены периода выполнит другой запрос.
- Сохранять квитанции при редактировании номера — оставит старые начисления в intent при новом номере.

## Условия пересмотра

Новый формат журнала, многопользовательская авторизация, иной контракт идемпотентности backend или изменение долговечности хранилища требуют отдельного решения и миграционного сценария. Запись перед отправкой и сверка результата остаются обязательными.
