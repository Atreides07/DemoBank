# Движение с пользовательской задачей

Основание — R-07, UI-08 и MOT-01…MOT-12 в `requirements.md`. Основной сценарий: пользователь читает историю и должен понять, какие операции остались, появились, изменились или исчезли после фильтра и сетевого обновления, сохранив ориентир чтения. Сворачивание баланса — вспомогательное объяснение иерархии экрана.

## Что объясняет движение

| Событие | Поведение и мотивация |
| --- | --- |
| Смена фильтра | Сохранившиеся записи переходят на новые места с прежней идентичностью; исключённые исчезают. Видно, что изменился состав, а не объект под пальцем. |
| Новая операция во время чтения | Фича сохраняет текущие данные и предлагает `DsPendingUpdates`. Нажатие «Показать обновления» применяет согласованный набор; само поступление ответа не уводит пользователя в начало. |
| Новые записи перед видимой строкой | Первый сохранившийся видимый ориентир удерживается корректировкой прокрутки. Остальные смещения связывают прежний и новый порядок. |
| Обновление статуса | Сохраняется id записи и состояние её элемента; содержимое меняется внутри знакомой строки. Фича может передать `changed` для явной отметки обновления. |
| Удаление строки из выборки | Строка теряет непрозрачность и освобождает место. Сразу перестаёт участвовать в озвучивании и нажатиях. |
| Быстрый повторный фильтр | Новый переход начинается из текущих визуальных положений, а не из начала предыдущего сценария. |
| Жест пользователя | Корректировка якоря прекращается при изменении прокрутки пользователем. Движение не борется с пальцем. |
| Уменьшение анимации | Состав обновляется немедленно с теми же id, доступными подписями и сохранением контекста. |

Итоговые финансовые значения обновляются из состояния данных. Анимация не считает деньги и не показывает интерполированные вымышленные суммы. Ни один запрос и ни одно действие оплаты не ждёт окончания визуального перехода.

## Реализация

`DsAnimatedSliverList<T>` принимает неизменяемый список моделей, `idOf`, `itemBuilder`, общий `ScrollController` и семантический переключатель `animate`. `onAnchorChanged` сообщает первый видимый стабильный id после компоновки с учётом перекрытия закреплённым заголовком; повторные сообщения того же id исключены, перестроение списка для сообщения не выполняется. Фича может сохранять окно данных вокруг этого якоря при обновлении. Строки строятся лениво через `SliverChildBuilderDelegate`. `findChildIndexCallback` сопоставляет ключи и новые позиции, сохраняя состояние элементов после перестановок. Одинаковый id дважды вызывает явную ошибку; индекс массива не используется вместо идентичности операции.

Перед изменением фиксируются текущие визуальные положения только смонтированных строк. После компоновки рассчитывается разница положений; преобразование каждой строки плавно уходит к нулю. Повторное обновление фиксирует положение с учётом незавершённого преобразования. Для исключённых записей временно удерживается соседняя позиция и уменьшается занимаемая высота; удаление завершает переход. Повторное появление той же записи прерывает уход без создания второго интерактивного элемента.

Для ухода удерживаются только смонтированные строки, включая ленивый буфер. Удалённые далеко за экраном записи сразу освобождаются: они не занимают фиктивную высоту и не требуют таймера анимации. Массовая смена префикса иначе может размонтировать сохранившуюся опору ещё до post-frame коррекции. Внутренний элемент sliver сохраняет её уже известный layoutOffset при штатном remap ключей; RenderSliverList продолжает компоновку от этой точной опоры. Неизвестные высоты не угадываются, весь префикс не строится. Абсолютная система scroll pixels может уточняться при достижении начала, а инвариантом остаются видимая координата и State сохранившейся строки. Проверяются также частично видимая строка и возврат к обоим краям без пустой области.

Анимация каждой смонтированной строки владеет своим контроллером и границей перерисовки. Её `AnimatedBuilder` повторно использует ребёнка; тело строки и весь список не перестраиваются на каждом кадре. Список меняет состояние при новом наборе и завершении удалений. Операции не хранятся в дизайн-системе после удаления из переданного набора и окончания ухода. Параметры задержек сети находятся в симуляторе, а не в виджетах.

Штатное движение использует общую кривую и токен непрерывности 360 мс. Это исходная настройка дизайн-системы, а не показатель производительности. `animate: false` обеспечивает вариант корректного немедленного обновления для сравнения пользы. Уменьшение движения учитывается также при изменении системного параметра в середине перехода.

`DsCollapsingHeader` использует `SliverPersistentHeader(pinned: true)`. Его геометрия непосредственно зависит от позиции прокрутки: развёрнутый баланс и компактная панель являются одним непрерывным представлением. Дополнительный таймер не конкурирует с жестом. Масштаб текста влияет на доступную высоту заголовка.

`dsRoute` ограничивает переход входящей поверхностью экрана. Столбцы инфографики меняют визуальные пропорции по общим токенам, а точные подписи сразу отражают согласованное состояние данных. Идентификатор выбранной точки сохраняет связь с детализацией.

`DsReadingSurface(child: scrollSurface, notice: ...)` размещает уведомление о новых данных поверх нижней части поверхности в пределах SafeArea. Оно остаётся доступным при глубокой прокрутке и не добавляет новый sliver перед читаемой строкой. Появление, нажатие действия и исчезновение уведомления не меняют ограничения дочерней прокрутки, её offset и положение строки. Доступная область уведомления объявляется как live region. Решение о применении обновления и содержание действия остаются у фичи.

`DsTransitionPage<T>` адаптирует `dsRoute` к декларативному Navigator и go_router без зависимости от конкретного роутера. Ключ, имя, аргументы и restoration id передаются через Page. При обновлении Page с тем же ключом маршрут читает новое содержимое из текущих settings, сохраняя корректность повторного построения и общие токены движения.

## Воспроизводимые проверки

Widget-тесты `packages/design_system/test/motion_list_test.dart` проверяют:

- Сохранение состояния четырёх строк при перестановке и повторном изменении во время перехода.
- Непрерывность визуального положения строки при повторном переходе.
- Добавление новой строки перед читаемой записью: тот же визуальный якорь, соответствующее изменение scroll offset.
- Возможность немедленно продолжить жестом прокрутки после обновления.
- Недоступность уходящей строки для озвучивания и отсутствие дубля при быстром повторном появлении.
- Немедленный вариант при системном уменьшении движения и отсутствие оставшегося тикера.
- Явный отказ на повторяющиеся id.
- Массовое удаление и вставка в наборе 12 000 строк с разной высотой: точные координаты и State полностью и частично видимой опоры, меньше 50 смонтированных строк, корректные начало и конец после обратной прокрутки.

Оболочка сохраняет scroll surface при появлении overlay уведомления, вместо перестроения счетов и заголовка. Встроенное действие истории отключается только у host, который уже предоставляет overlay; остальные hosts сохраняют своё действие. При применении нового фильтра фича возвращает к началу, если прежней опоры больше нет в результате. Ожидающий или ошибочный запрос этого не делает. Переключатель сравнения подписан на свой флаг явно и проверяется по фактическому `HistorySliver.animate`, без зависимости от случайной смены темы.

Кнопки категорий имеют отдельную подписку на применённую категорию через `BlocSelector`. При обновлении статусов, числа операций и ожидающего окна используется тот же виджет фильтров; изменение категории обновляет его собственной подпиской. Это исключает повторное построение неизменившейся ветки во время применения нового окна. Проверка реальными нажатиями подтверждает: до ответа выбран прежний фильтр, успешный ответ меняет выбор, ошибка сохраняет прежний выбор. Причинные widget-трассы используются отдельно от обычного численного profile-прогона: их дополнительная нагрузка не выдаётся за пользовательскую скорость.

Каждая смонтированная строка истории сохраняет только своё текущее DS-содержимое. Оно заменяется при изменении отображаемой даты, суммы и валюты, названия, категории, статуса, отметки обновления или состояния повторной загрузки. Общего кеша виджетов для всей истории нет. Обработчики читают последнюю модель и callback из State; тема и MediaQuery разрешаются внутри DS-потомков. Widget-тесты проверяют актуальность деталей по нажатию, обновление всех видимых значений, смену темы и 200% текста без потери строки.

Тесты дизайн-системы отдельно проверяют высоты операции и её кеш-заглушки при 100% и 200%, а также сворачивание и повторное раскрытие закреплённого заголовка. Интеграционные проверки оболочки должны дополнить это ответами вне очереди, ошибкой страницы, сменой фильтров и контролем ограниченного кеша через настоящий сетевой контракт.

## Проверка пользы и производительности

Техническая работоспособность перехода не равна подтверждённой пользе. Для приёмки MOT-11/MOT-12 нужно сравнить две версии на одинаковых данных и одинаковом сетевом сценарии: полный переход и `animate: false`.

Задание: начать чтение указанной операции, применить фильтр или новые данные, найти изменившуюся запись, объяснить изменение и продолжить просмотр. Порядок версий чередуется. Записываются время, повторный поиск, потеря места, неверные нажатия и способность объяснить результат. Если преимущество не проявляется, движение и сценарий пересматриваются. В репозитории до такой сессии нельзя отмечать человеческую приёмку как пройденную.

На выбранном физическом бюджетном Android отдельно записываются profile trace при прокрутке, фильтре, поступлении страницы и прерывании; длительность кадров UI/raster, пропущенные кадры, задержка взаимодействия и память. Измерения локального widget runner или десктопного браузера не заменяют эту проверку.


После первой пользовательской проверки прежний визуальный дизайн отклонён. Переработка DS-23—DS-26 сохраняет алгоритм анимации истории и её мотивацию; меняет палитру, плотность и постоянную навигацию. Польза полного перехода по MOT-11/MOT-12 не считается подтверждённой ответом о дизайне. Новые численные профили и повторная пользовательская оценка связываются с текущим снимком в `verification.md` и `user-acceptance.md`.
